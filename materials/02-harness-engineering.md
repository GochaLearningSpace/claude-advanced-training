# 2. Harness Engineering(20分・ハンズオン)

対象: `samples/common-web`(MiniTask)を各自の Claude Code で操作。

## 定義(1分で話す)
ハーネス = エージェントループ + 権限システム + ツール定義 + フィードバックループの総体。今日は「動くハーネス」を実際に手で組み立てて体感する。

## 手順

### Step 1: hook でエージェント行動を可視化する(7分)

MiniTask の `.claude/settings.json` に PostToolUse hook を追加させ、Edit/Write の度に `.claude/harness.log` へ1行追記させる。

> **講師確認事項(当日までに必須)**: hook に渡される JSON のフィールド名(`tool_name` 等)は Claude Code のバージョンによって変わりうる。当日の Claude Code バージョンで公式の hooks リファレンスを確認し、下記スニペットのコマンド部分を実際の環境で動作確認してから配布すること。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "<公式ドキュメントで確認したstdin JSONを整形し .claude/harness.log に1行追記するコマンド>" }
        ]
      }
    ]
  }
}
```

書けたら実際に MiniTask のファイルを1つ編集させ、`.claude/harness.log` に記録が残ることを確認させる。

**この時点でのログはただの生ログ。5. Log Engineering セクションでこれを構造化フィールドへ拡張する** — 伏線として明示する。

### Step 2: 権限スコープを書いて、壊して、直す(6分)

まず、あえて過剰な権限設定を書かせる:

```json
{
  "permissions": {
    "allow": ["Bash(*)", "WebFetch(*)", "Write(*)"]
  }
}
```

書かせた後に問う: 「このエージェントに今、何ができてしまうか?」→ 議論(1分)。

その後、MiniTask の開発で実際に必要な操作だけに絞らせる:

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Bash(git *)", "Edit(samples/common-web/**)"]
  }
}
```

**ポイント**: 「最小権限」は抽象論ではなく、実際に許可リストを削る作業そのものだと体感させる。

### Step 3: 検証ループの実例を見る(4分・講師デモ)

講師の Real Estate Simulator プロジェクトの `Self-Tests` カスタムメニューを画面共有で実演。「ハーネスに検証機構が無いと、チャートのシリーズがずれるようなバグは誰も気づかない」という実例で、フィードバックループの必要性を示す。

学生への問いかけ: 「MiniTask に同じ発想の検証ステップを足すなら、何を確認する?」→ 口頭で2〜3人に答えさせる(実装はしない、時間の都合)。

### Step 4: Claude Cowork との対比(3分・ディスカッション)

Claude Cowork の設計原理を紹介:
- **outcomes**: 手順でなくゴールを指定する制御方式
- **webhooks**: 外部システムからのトリガーでエージェントが起動する仕組み

問いかけ: 「Step 1 で書いた hook はステップ指定型の制御。もし MiniTask のタスク追加を『ゴール指定型』で書くとしたら、どう変わる?」「タスク追加を外部トリガー(Slack通知など)で起動するなら、webhooks的に何を仕込む?」

→ 実装はしない。ハーネス設計に「ステップ指定 ⇔ ゴール指定」というスペクトラムがあることを伝えるのが目的。

## 講師メモ
- Step 1 の hook 実装が動かない学生が出る前提で、講師手元で動作確認済みのコマンドをコピペで渡せるようにしておく(当日のトラブルシューティング時間を食わないため)
- Step 2 は「壊してから直す」体験が肝。先に正解を見せない
